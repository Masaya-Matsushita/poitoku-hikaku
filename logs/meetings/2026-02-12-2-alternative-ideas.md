## 1. オーナーが実現したいこと

### 最終目標

**個人開発で月数万円程度の副収入を得る仕組みを作る**

### 理想の条件

| 条件 | 詳細 |
|------|------|
| 競合が少ない | 大企業が参入しにくい領域 |
| 高額な報酬 | 1件あたり数百円〜数千円 |
| メンテナンス工数が低い | AIクローリングで自動化 |
| 市場が成長している | 将来性がある |
| **リンクを踏むだけで報酬** | ★新規登録不要であること（重要） |

### その他のモチベーション

収益化だけが目的ではない。以下も重要な動機：

- **新たな知識・経験を得ること**（プロダクトのオーナーシップ、AI活用、自動化など）
- **楽しさ駆動で開発できること**（本業とは別の「遊び場」）
- **ワンチャンに夢を見られること**（うまくいったらラッキー、労働による収入でなく自動で稼げる「仕組み」をつくる）

→ 収益化の確度が低くても、これらが満たされるなら続ける価値がある。

### 投資可能なリソース

| 項目 | 上限 |
|------|------|
| 初期投資 | 5〜10万円 |
| 月額コスト | 1,000〜3,000円程度 |
| 時間 | 片手間（本業あり） |

## 2. ポイ活比較で学んだこと

### 当初の構想

「ポイントサイトの案件を横断検索・比較できるWebサービス」を作り、紹介報酬で収益化する。

### 選定理由（筋が良かった点）

| 理由 | 評価 |
|------|------|
| 競合が少なさそう | △ 実際には「どこ得？」など複数存在 |
| 紹介料1,000円 | ✅ 正しい |
| AIでメンテフリー | △ スケール時にコスト増（工夫で抑制可能） |
| ポイ活への関心増加 | ✅ 正しい |
| **クローリングがグレーで大企業が参入しにくい** | ✅ 正しい |

### 発覚した問題

#### 問題1: 収益化モデルの構造的な難しさ

```
ポイ活比較の収益構造:

1. ユーザーが比較サイトで案件を検索
2. 「ハピタスが一番お得」と分かる
3. ユーザーがハピタスに移動

ここで分岐:
  A) 紹介リンク経由で新規登録 → 報酬発生 ✅
  B) 直接サイトにアクセス → 報酬ゼロ ❌
  C) 既にアカウントを持っている → 報酬ゼロ ❌

問題: B と C のケースが多い
```

**「比較サイトとして価値を提供しても、新規登録がなければ報酬が発生しない」**という構造的な問題がある。

#### 問題2: 集客の難しさ

| 集客方法 | 課題 |
|----------|------|
| SEO | 競合のドメインパワーに負ける、6ヶ月〜1年かかる |
| SNS | 継続的な発信が必要、労力がかかる |
| 広告 | コストが高く、赤字になる |

#### 問題3: 競合の存在

| サービス | 対応サイト数 | 運営年数 |
|----------|------------|---------|
| どこ得？ | 50+ | 15年 |
| ポイント獲得ナビ | 16 | 不明 |
| Mark Point | 26 | 不明 |

### 学びのまとめ

1. **競合調査は最初にやる** - 思ったより競合がいることが多い
2. **SEOは甘くない** - ドメインパワーの壁は高い
3. **「メンテナンスフリー」は幻想** - コストか手間、どちらかは必要
4. **スケール時のコストを試算する** - 小規模では見えない問題がある
5. **集客を先に考える** - 作っても人が来なければ意味がない
6. **「勝つ」必要はない** - 自分の導線があれば価値がある
7. **収益化モデルを先に検証する** - ★今回の最大の学び

## 3. 新規プロジェクトの候補

### オーナーの希望

> 「案件や商品へのリンクがそのまま紹介リンクになっていて、利用者が踏むだけで私にも一部還元されるようなものが理想」

これは**アフィリエイト型**の収益モデル。ポイ活（紹介報酬型）とは異なる。

### 候補一覧

| 候補 | 報酬モデル | 報酬額 | 競合 | 推奨度 |
|------|-----------|--------|------|--------|
| ふるさと納税 | アフィリエイト | 寄付額の1〜3% | △ 比較サイト多いが速報型は少ない | ★★★ |
| 格安SIM | 紹介報酬 | 2,000〜5,000円 | △ 多い | ★★ |
| 証券口座 | 紹介報酬 | 5,000〜20,000円 | △ 多い | ★★ |
| 電力・ガス | アフィリエイト | 500〜3,000円 | ○ 地域別は少ない | ★★ |

### 他の候補について（検討の余地あり）

- **格安SIM / 証券口座**: 報酬は高いが「新規登録必須」のためポイ活と同じ問題を抱える。ただし報酬単価が高いため、少数の成約でも収益になる可能性はある
- **電力・ガス**: アフィリエイト型で「リンク経由の契約で報酬」。電気代高騰で乗り換え需要が増えている。地域別の比較は競合が少なく、ふるさと納税がうまくいかなかった場合の次の候補として検討の余地あり

### 推奨: ふるさと納税「高還元案件」速報

#### 選定理由

| 条件 | ふるさと納税 | ポイ活比較 |
|------|-------------|-----------|
| 報酬発生条件 | **リンク経由の寄付** | 新規登録必須 |
| 既存ユーザー | **報酬あり** | 報酬なし |
| リピート | **毎年寄付する** | 1回きり |
| 競合 | 比較サイトは多いが「速報」は少ない | 強い競合あり |

**ふるさと納税は「リンクを踏むだけで報酬」の条件を満たす。**

#### 収益試算

```
報酬率: 1〜3%（サイトによる）
平均寄付額: 30,000円
1件あたり報酬: 300〜900円

月1万円を稼ぐには:
- 300円/件の場合: 月34件の寄付
- CVR 2%なら: 月1,700訪問が必要
```

ポイ活と同様に集客は課題だが、**「既存ユーザーからも報酬が発生する」**のは大きなメリット。

#### 季節変動

```
ふるさと納税の寄付時期:
- 1〜10月: 少ない
- 11〜12月: 全体の50%以上が集中
```

年末に向けて需要が爆発する。

## 4. 推奨アプローチ: SNSファースト + 異常値検知

### アプローチ概要

ポイ活比較で出たアイデア「異常値検知 → SNS通知」をふるさと納税に適用する。

```
日次クローリング
  ↓
異常値検知（還元率50%超え、人気商品の在庫復活など）
  ↓
開発者に通知（Slack / Discord / LINE）
  ↓
確認後、SNSに投稿（手動 or ワンクリック）
  ↓
投稿内のリンクがアフィリエイトリンク
  ↓
ユーザーがリンク経由で寄付 → 報酬発生
```

### このアプローチの利点

| 観点 | 評価 |
|------|------|
| 初期コスト | 低い（サイト構築を後回しにできる） |
| 運用負荷 | 低い（通知を見て投稿するだけ） |
| 集客検証 | 先にできる（サイトなしでもSNSは始められる） |
| 技術的面白さ | ある（異常値検知のロジック設計） |
| 撤退しやすさ | 高い（サイトを作る前なら損失が小さい） |
| **収益モデル** | **アフィリエイト型（リンクを踏むだけで報酬）** |

## 5. ポイ活比較で設計した技術構成（参考）

新規プロジェクトでも流用可能な設計を以下に記載する。

### 技術スタック

| レイヤー | 技術 | 選定理由 |
|----------|------|----------|
| フロントエンド | Next.js (App Router) | SSG/ISRによるSEO最適化、Vercelとの親和性 |
| 言語 | TypeScript | 型安全な開発 |
| スタイリング | Tailwind CSS + shadcn/ui | 高速なUI開発 |
| クローラー | Python + Crawl4AI | AIクローリング（LLM抽出） |
| LLM | gpt-4o-mini | コスト効率（月$1-3程度） |
| DB | Supabase (PostgreSQL) | 無料枠あり、RLS対応 |
| ホスティング | Vercel | 無料枠あり |
| 自動実行 | GitHub Actions | 日次クローリング |

### ハイブリッド方式（推奨）

LLM抽出のコスト問題を解決するため、以下のハイブリッド方式を推奨。

```
新サイト追加時: LLMでCSSセレクタを自動生成
日次クローリング: CSSセレクタで実行（コストゼロ）
HTML変更検知時: LLMで再生成
```

- 初期設定だけLLMを使う
- 日次コストはゼロ
- **「メンテナンス発生時の対応コスト削減」がLLMの価値**

### データベース設計（参考）

```sql
-- 案件/返礼品データ
CREATE TABLE items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  site_name VARCHAR(50) NOT NULL,        -- 例: 'rakuten', 'satofuru', 'furunavi'
  item_name VARCHAR(255) NOT NULL,       -- 返礼品名
  donation_amount INTEGER NOT NULL,      -- 寄付金額
  market_value INTEGER,                  -- 市場価格（推定）
  return_rate DECIMAL(5,2),              -- 還元率（%）
  category VARCHAR(100),                 -- カテゴリ
  url VARCHAR(500) NOT NULL,             -- 商品ページURL
  affiliate_url VARCHAR(500),            -- アフィリエイトリンク
  fetched_date DATE NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  UNIQUE(site_name, url, fetched_date)
);

-- 異常値検知用: 過去データとの比較
CREATE INDEX idx_items_site_item ON items(site_name, item_name);
CREATE INDEX idx_items_return_rate ON items(return_rate DESC);

-- クローリングログ
CREATE TABLE crawl_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  site_name VARCHAR(50) NOT NULL,
  crawl_date DATE NOT NULL,
  total_count INTEGER NOT NULL,
  success_count INTEGER NOT NULL,
  error_count INTEGER NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

## 9. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| 還元率の計算誤り | 信頼性低下 | 手動確認を挟む、複数ソースで検証 |
| サイトのHTML変更 | クローリング失敗 | ハイブリッド方式（LLM + CSS） |
| アフィリエイト審査落ち | 収益化不可 | 複数サイトに申請、実績を作る |
| SNSアカウント凍結 | 集客不可 | 自動投稿を避ける、規約を遵守 |
| 季節変動（1〜10月） | 収益減少 | 年末に向けてフォロワーを増やす |

## 補足: ポイ活比較プロジェクトの状態

ポイ活比較（poitoku-hikaku）は**一時停止中**です。

- 技術的には実現可能
- しかし収益化モデルの構造的な難しさがある
- 再開する場合は、ハイブリッド方式 + SNSファースト + 異常値検知を検討

ふるさと納税プロジェクトでの学びを、将来的にポイ活比較に還元することも可能です。
