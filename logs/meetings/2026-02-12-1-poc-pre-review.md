### 2. 技術的懸念点（Claudeの分析）

#### Crawl4AI + LLM抽出の精度リスク

- 「HTML変更に強い」という前提が未検証
- ポイント表記のバリエーション対応が不明
  - `10,000P`（単純）
  - `最大10,000円相当`（「最大」を除去できるか）
  - `10,000P + 最大5,000Pボーナス`（どちらを取るか）

#### コスト見積もりの不確実性

| 規模 | 月間コスト（推定） |
|------|-------------------|
| 2サイト × 100件 | 月$1-3（約500円） |
| 20サイト × 1,000件 | 月$300（約45,000円） |

**スケールするとコストが爆発する**という問題が判明。

### 3. ビジネス観点の懸念（Claudeの分析）

#### 競合の存在

| サービス | 対応サイト数 | 運営年数 |
|----------|------------|---------|
| どこ得？ | 50+ | 15年 |
| ポイント獲得ナビ | 16 | 不明 |
| Mark Point | 26 | 不明 |
| **ポイ得比較（当サービス）** | 2（MVP） | 0年 |

**2サイトでは比較サービスとしての価値がほぼない**。

#### SEOの厳しさ

- 「ポイントサイト 比較」で上位表示は困難
- ドメインパワー（運営年数、被リンク数）で競合に負ける
- GoogleはE-E-A-T（経験・専門性・権威性・信頼性）を重視
- ロングテールキーワードなら可能性あり

#### 収益化の現実

```
目標: 月1万円
紹介報酬: 1人あたり約1,000円
必要登録数: 月10人
登録CVR 1% → 月1,000訪問が必要
```

**不可能ではないが、簡単でもない**。

### 4. Ollamaへの移行検討

オーナーの懸念：「月1万の収益が厳しいならランニングコストを掛けていられない」

#### Ollamaの仕組み

```
OpenAI API: あなたのPC → OpenAIサーバー → 課金
Ollama: あなたのPC内のLLM → 無料
```

#### 現実的な問題

| 方式 | コスト | 問題 |
|------|-------|------|
| GitHub ActionsでOllama | 無料 | スペック不足でLLMが動かない |
| 自分のPCでOllama | 無料 | 毎日PCを起動する必要あり |
| クラウドVPSでOllama | 月$5〜20 | OpenAI APIより高くなる可能性 |

**結論**: OpenAI APIの月500円程度は非常に安い。Ollamaに移行するメリットは薄い。

### 5. API公開の検討と撤回

オーナーの質問：「ChatGPT等のLLMに『ポイ得比較』を紹介してもらえないか？」

Claudeの提案（後に撤回）：
- GPTs + Actions で API連携
- Claude MCP Server として公開

**撤回理由**:
```
通常の流れ: ユーザー → Webサイト → 紹介リンク → 報酬
API経由: ユーザー → LLM → API → データ取得（紹介リンクを踏まない）
```

API公開は副収入目的には適さない。

### 6. 根本的な問題の発覚

オーナーの計画：「一般公開時には20サイト × 数千件を想定」

これによりコスト問題が顕在化：
- 月4〜5万円のAPI費用
- 個人開発として現実的ではない

#### Crawl4AI選定の前提が崩れた

| 当初の前提 | 現実 |
|-----------|------|
| LLM抽出でメンテナンスフリー | スケール時にコストが爆発 |

#### 競合の戦い方

どこ得？（50+サイト対応）は**CSSセレクタ抽出**を使用（推測）。

| 方式 | API費用 | メンテナンス |
|------|--------|-------------|
| LLM抽出 | 高い | 不要 |
| CSSセレクタ | **ゼロ** | HTML変更時に修正 |

競合が15年間CSSセレクタでやってこれた理由：
- HTML構造は頻繁には変わらない
- 変わっても修正は数時間で済む
- API費用ゼロで利益率が高い

## セカンドオピニオン（別AIからのフィードバック）

オーナーが第1回壁打ちの議事録を別のAIに読ませ、意見を求めた。

### 別AIからの指摘

#### 1. スケール時のコスト試算が極端

> 20サイト × 1,000件 = 月$300（約45,000円）という試算は「全案件を毎日LLMで処理する」前提だが、実際には：
> - 差分更新（新規・変更分のみLLM処理）で大幅に削減可能
> - キャッシュ戦略（同一ページは再処理しない）
> - 案件数は1サイトあたり数百件程度（数千件は過大見積もり）
>
> 現実的には20サイトでも月$10-30程度に抑えられる可能性がある。

#### 2. CSSセレクタ vs LLM の二項対立になっている

> ハイブリッド方式がもっと深掘りされるべき。
>
> LLMの本当の価値:
> - 初期セットアップの省力化
> - HTML構造変更の「検知」（抽出失敗 → 再生成）
> - 日次処理はCSSセレクタで十分
>
> Crawl4AI を選んだ理由は「メンテナンスフリー」ではなく「メンテナンス発生時の対応コスト削減」と捉え直すべき。

#### 3. 「どこ得？に勝てない」は正しいが、勝つ必要があるのか？

> - MVP は「仕組みの検証」が目的だったはず
> - 2サイトで技術検証 → 10サイトに拡大 → 価値が出始める
> - 「どこ得？の下位互換」でも、自分の紹介リンク経由なら価値がある
>
> 競合に勝つのではなく、「自分の紹介コードで登録してもらう導線を作る」という目的なら、50サイト対応は不要。

#### 別AIの結論

> 後ろ向きになるのは早い。PoC は予定通り実施すべき。
>
> | 懸念 | 現実的な対応 |
> |------|-------------|
> | スケール時のコスト | 差分更新で抑制可能 |
> | 競合に勝てない | 勝たなくてもいい。自分の紹介リンク導線があれば価値 |
> | SEOで負ける | ロングテール + SNS でニッチを狙う |

### SNS自動化の検討

オーナーの質問：「SNS運用をAIに任せられないか？」

#### SNS自動化の現実

| 機能 | AIで可能か |
|------|-----------|
| 投稿文の生成 | ✅ 可能 |
| 自動投稿 | ✅ 可能（Buffer等、月$15〜） |
| フォロワーを増やす | ❌ 難しい |

## 新しいアイデア：異常値検知 → SNS通知

オーナーからの提案：

> SNSで有益な情報だけを静かにたれながすアカウントは需要無いかな。
> 例えば「楽天カードがモッピーで過去最高額」など。
> Crawl4AIで集めてきた情報をもとに、もし特徴的なデータがあれば開発者（私）に通知するような仕組みを作れば一定簡単に運用できそう。

### このアイデアの評価

| 観点 | 評価 |
|------|------|
| 毎日発信する必要 | ❌ 不要（異常値があるときだけ） |
| 人格を出す必要 | ❌ 不要（情報の価値だけで勝負） |
| 自動化のしやすさ | ✅ 高い |
| ポイ活界隈での価値 | ✅「速報」には価値がある |

**再開時に検討する価値あり**。

### 実装イメージ

```
日次クローリング
  ↓
異常値検知（過去最高額、急上昇、期間限定など）
  ↓
開発者に通知（Slack / Discord / LINE）
  ↓
確認後、SNSに投稿（手動 or ワンクリック）
```

- 完全自動投稿ではなく「通知 → 確認 → 投稿」
- 人間のフィルターを通すことで品質担保
- 運用負荷は低い

## 再開する場合の選択肢

### 選択肢1: CSSセレクタ抽出に切り替え

```
日次クローリング: CSSセレクタ（コストゼロ）
HTML変更時: 手動で修正（月1〜2回程度）
```

- コスト: ほぼゼロ
- デメリット: メンテナンス作業が発生
- **競合と同じ戦い方になる**

### 選択肢2: ハイブリッド方式（推奨）

```
新サイト追加時: LLMでCSSセレクタを自動生成
日次クローリング: CSSセレクタで実行（コストゼロ）
HTML変更検知時: LLMで再生成
```

- 初期設定だけLLMを使う
- 日次コストはゼロ
- **現実的な落としどころ**

### 選択肢3: 規模縮小

```
5サイト × 100件 = 500件/日
月コスト: 約1,000円程度
```

- 比較サービスとしての価値は下がる
- でもコストは許容範囲

### 選択肢4: SNSファースト + 異常値検知

```
1. まずSNSでポイ活情報を発信開始
2. クローリング基盤を構築し、異常値検知を実装
3. 「過去最高額」「期間限定」などを検知したら通知
4. 確認後、SNSに投稿
5. フォロワーが増えてきたらサイトを作る
```

- サイト構築を後回しにできる
- 集客の検証を先にできる
- **新しいアプローチとして検討の価値あり**

実は、一番バランスが良い案の可能性
  ┌──────────────┬─────────────────────────────────────────────┐
  │     観点     │                    評価                     │
  ├──────────────┼─────────────────────────────────────────────┤
  │ 初期コスト   │ 低い（サイト構築を後回しにできる）          │
  ├──────────────┼─────────────────────────────────────────────┤
  │ 運用負荷     │ 低い（通知を見て投稿するだけ）              │
  ├──────────────┼─────────────────────────────────────────────┤
  │ 集客検証     │ 先にできる（サイトなしでもSNSは始められる） │
  ├──────────────┼─────────────────────────────────────────────┤
  │ 技術的面白さ │ ある（異常値検知のロジック設計）            │
  ├──────────────┼─────────────────────────────────────────────┤
  │ 撤退しやすさ │ 高い（サイトを作る前なら損失が小さい）      │
  └──────────────┴─────────────────────────────────────────────┘

### 選択肢5: プロジェクト再検討

- ポイントサイト比較は競合が強い

## 補足: 学びのまとめ

### 個人開発で副収入を得るために重要なこと

1. **競合調査は最初にやる** - 思ったより競合がいることが多い
2. **SEOは甘くない** - ドメインパワーの壁は高い
3. **「メンテナンスフリー」は幻想** - コストか手間、どちらかは必要
4. **スケール時のコストを試算する** - 小規模では見えない問題がある
5. **集客を先に考える** - 作っても人が来なければ意味がない
6. **「勝つ」必要はない** - 自分の導線があれば価値がある

### このプロジェクトで良かった点

1. ドキュメントを先に整備した
2. PoC前にレビューを実施した
3. セカンドオピニオンを取得した
4. 実装前に問題に気づけた
5. $10と数日の投資で済んだ

### セカンドオピニオンの価値

- 一人のAIの分析には偏りがある
- 複数の視点を得ることで、より客観的な判断ができる
- 今回は「極端な悲観」を修正できた

## 追記: ポイ活比較サイトの構造的な難しさ

### 収益化モデルの構造的な難しさ

ポイ活比較サイトの収益化には、以下の構造的な問題があることが判明した。

#### 紹介報酬型の収益構造

```
収益発生の条件:
1. ユーザーが紹介リンク経由でポイントサイトにアクセス
2. そのサイトで「新規アカウント作成」
3. 報酬発生

問題点:
- 既存ユーザーからは収益ゼロ
- 直接サイトに行った人からも収益ゼロ
- 比較サイトとして価値を提供しても、「新規登録」がなければ報酬なし
```

#### 他の収益モデルとの比較

| モデル | 報酬発生条件 | 報酬額 | 難易度 |
|--------|-------------|--------|--------|
| **紹介報酬型**（ポイ活） | 新規登録が必要 | 高い（1,000〜2,000円） | **難しい** |
| **アフィリエイト型**（EC等） | リンク経由の購入 | 低い（1〜10%） | 比較的簡単 |

**ポイ活比較は「紹介報酬型」であるため、収益化のハードルが高い。**

#### この問題への対応策

1. **SNSで紹介リンクを直接訴求** - 比較サイトを介さずに紹介
2. **紹介報酬型ではない領域を選ぶ** - ふるさと納税など（別プロジェクトとして検討）

→ 別プロジェクトの検討内容は `2026-02-12-2-alternative-ideas.md` を参照
