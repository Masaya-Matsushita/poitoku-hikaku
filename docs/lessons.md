# 学び（lessons）

「何を作ったか」ではなく「何が想定と違ったか」を残す。第二弾以降のアイデア選定と設計判断に使う。
新しい学びは末尾に追記する。Routine も追記してよい（事実のみ。推測は「推測」と明記）。

## 2026-02（第一弾・構想時、一時停止）

- 競合調査は最初にやる。「競合がいなさそう」は大抵、調べていないだけ
- 「メンテナンスフリー」は幻想。コストか手間のどちらかは必ず要る
- LLM抽出はスケール時にコストが爆発する。日次処理にLLMを入れない
- SEOは甘くない。ドメインの年数と継続更新は時間でしか積めない
- 集客を作る前に、収益モデルの発生条件を確認する。「価値を提供しても報酬が出ない」構造がある
- セカンドオピニオン（別AI）で極端な悲観が修正された。判断の前に複数の視点を取る

## 2026-09（第一弾・再始動時）

- 前提が変わると要件が反転する。「メンテを減らす」は AI主導では「メンテはAIがやる」になり、半年前の最大の懸念が自律ループの最初の題材になった
- 紹介報酬は「登録時」ではなく「登録者が案件を利用した後」に発生する（モッピー：友達が180日以内に300P獲得で紹介者に300P）。収益試算は登録数ではなく活動者数で置く
- ダウン報酬（紹介した人の獲得ポイントの数%）が収益の本体。時間とともに積み上がるので、早く始めるほど有利
- ASP（AppDriver / SKYFLAG）は実質B2Bで初期は使えない。個人が使える一般ASP（A8等）は補助にしかならない
- 最大の法的リスクは訴訟ではなく会員アカウント停止。クロールの節度は法的防御ではなく「運営を不快にさせない」ための線
- GCP静的ホスティングは独自ドメインHTTPSにLB（有料）が必要。Firebase Hosting なら無料
- 「上限0円」は上限設定ではなく「支払い手段を持たない」で実現する。GCPにハードキャップはない
- Vercel Hobby は商用利用不可
- 機能を一気に作っても、価値は「データが貯まった日」から数えて立ち上がる。クローラーを最初に本番に置く
- 個人開発の参入障壁は「信頼」より「時間」（履歴データ、ドメイン年数、ダウン報酬の積み上げ）
- Supabase の「既定の権限付与」は `postgres` ロールが作ったテーブルにしか付かない。ローカル CLI のリンク経由（一時ログインロール）で適用した初回スキーマには service_role の GRANT が無く、RLS ポリシーがあっても secret key で書けなかった。dry-run では気づけない（DB に書かないため）。テーブルを作るマイグレーションには GRANT を明示する
- CI のランナーは IPv6 を持たず、Supabase の DB 直結（IPv6 のみ）ができない。プーラー（IPv4）へ `--db-url` で直接つなぐのが最も依存が少ない。`supabase link` はスコープを絞った Personal Access Token では通らない（API キー閲覧を要求する）
- 「一致する実測値」は書き込みまでは保証しない。本番の初回は dry-run ではなく書き込みまで通して初めて検証になる
- 「数値化できない」には 3 種類ある：セレクタが外れた（reward_raw が空）、還元が無い（「ポイント対象外」→ 0）、還元がポイントでない（物品プレゼント→ 数値 null のまま）。KPI の分母で区別しないと Routine が最後の種類を修復しようとする
- GitHub Actions の scheduled 実行は毎時 0 分だと大きく遅れる（cron 18:00 UTC が 21:10 UTC に開始、3 時間遅延）。1 日 1 回の要件は満たすので当面は許容。遅延が問題になったら分を 0 以外にする
- サイトの内部 API（ページの JS が呼ぶ AJAX）は、robots.txt で禁止されていなくても直接呼ぶと数回で拒否されることがある（ハピタスの `/item/ajaxcategoryitems` は 200 → 404 に変わった）。「運営を不快にさせない」線として、通常の閲覧者が読むサーバー描画のページだけを使う。モッピーの断片取得はページ自身の描画経路なので例外扱いではなく、同じ基準で「ページが読むものを読む」に留める
- GitHub Actions の bot（GITHUB_TOKEN）が作った PR でも pull_request の CI 実行は作られるが、bot が「初回貢献者」の間は承認待ち（action_required）で止まり、その承認待ちが PR のチェック判定を占有して必須チェックが未報告になる（workflow_dispatch で別に起動した成功チェックは無視された）。初回は人が承認し、以後は承認待ちを API で承認するフォールバックを入れた
- 半年前の調査メモ（2026-02）は半分正しく半分古い。ハピタスは「検索は JS」までは正しかったが、カテゴリページはサーバー描画で個別ページの巡回は不要だった。着手時に必ず実 HTML で再検証する

## 第二弾のアイデア選定基準（現時点、随時更新）

- 公開データが時間で変動し、履歴に価値が出る領域か
- 報酬が「リンクを踏むだけ」または「既存ユーザーからも」発生するか
- 大手には市場が小さすぎるか
- 0円インフラで運用が回るか
- 第一弾のパイプラインが流用できるか
