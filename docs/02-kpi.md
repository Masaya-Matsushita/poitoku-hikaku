# 02 — KPIと計測

夜間の自律改善ループは「何を改善と呼ぶか」がなければ動けない。ここがRoutineの北極星。

## Phase 1〜2（データ収集期、最初の3ヶ月）

| KPI | 目標 | 計測方法 | Routineが取れるアクション |
|---|---|---|---|
| クロール成功率 | 95%以上（サイト×日） | `crawl_logs` | 失敗原因の分類、リトライ戦略調整、セレクタ修復PR |
| 抽出精度 | 99%以上（数値が取れた件数/取得件数） | `crawl_logs` ＋ サンプル検証 | セレクタ修復、正規化ルール追加 |
| 対象案件数 | 単調増加 | `crawl_logs.offer_count`（その日に一覧で取れた一意な案件数）と `offers` の件数。snapshots の保存方式（ADR-0005、変化があった時だけ保存）には依存しない | 収集範囲（カテゴリページ等）の拡張PR |
| 索引ページ数 | 単調増加 | Search Console（連携後） | sitemap・内部リンク・構造化データ改善 |
| コスト | 0円 | 各サービスのダッシュボード | 無料枠の残量を監視し、超えそうなら警告 |

### 抽出精度の読み方

`crawl_logs.parsed_count / offer_count` は「還元額を数値化できた割合」で、分母には **還元がポイントではない案件**が含まれる
（保険の一括見積・資料請求の物品プレゼント等。`reward_raw` に文言が入り、`reward_points` と `reward_percent` は null）。
これは修復対象ではなく、数値化率の実質的な上限を下げる要因。2026-09 時点でモッピーは 6 / 1,791 件（0.3%）。

- 真の抽出失敗は、当日掲載の案件（`offers.last_seen_on` = 当日）のうち、現在有効な還元額（`offer_snapshots.valid_to is null`）の `reward_raw` が **空**のもの。修復（セレクタ・数値化ルール）はこれだけを対象にする
- `reward_raw` に文言があって数値が null の行は、文言を見て「ポイントでない還元」なら放置、「新しいポイント表記」なら数値化ルールを足す
- 目標 99% は数値化率のまま据え置く。ポイントでない案件が増えて届かなくなったら、目標ではなく分母の定義を見直す

### 対象案件数の読み方

`crawl_logs.offer_count` は「その日に一覧で取れた案件数」なので、対象サイトが案件の掲載を終えれば、クローラーに問題が無くても減る
（2026-09-24〜26 にモッピー 1,791 → 1,748、ハピタス 2,773 → 2,747。どの日もエラー・打ち切りなし、リクエスト数は平常）。
日次レポートは減少を「要確認」に出し、内訳として **新規**（`offers.first_seen_on` = 当日）と **消えた**（`offers.last_seen_on` = 前日。前日は掲載、当日は未観測）を並べる。

- エラー・打ち切りが無く、リクエスト数も平常で、「消えた」が案件数の数 % 以内：対象サイト側の掲載終了。修復対象ではない
- リクエスト数が減っている、エラーがある、「消えた」が急に増えた：収集範囲の欠け。セレクタやカテゴリ発見を疑う
- 前日比 50% 未満は別の警告（構造変化の疑い、ADR-0003）

「単調増加」は収集範囲（カテゴリ・サイト）を広げる改善の向きを示す目標で、日々の掲載数の増減そのものではない。
内訳の数値が 1〜2 週間貯まったら、減少の警告を「消えた」の割合で出すかどうかを決める。

### 還元額の変化の読み方

日次レポートの「還元額の変化」は件数（当日に始まった区間の数 = 変わった案件 + 新規案件）に加え、サイトごとに変化の大きい上位 5 件を表で出す。

- 対象は当日に始まった区間のうち、同じ案件に直前の区間（`valid_to` が null でない最新）があるもの。新規案件は含めない
- 並びは `reward_points` の差（新 − 前、符号付き）の絶対値が大きい順、同じなら案件名順。前後どちらかが数値化できない案件（% 還元など）は上位に含めず「対象外 N 件」に数える
- 見るところ：桁違い・0 への急落は抽出の異常の疑い（セレクタや数値化ルールを確認）。実際の増減なら Phase 3 の「過去最高・買い時判定」で扱う変化の実物になる

## 計測の原則

- 計測できないものは改善対象にしない
- KPIは `docs/02-kpi.md`（このファイル）を単一の真実とし、Routineのプロンプトはここを参照する
- 日次のKPIスナップショットは `reports/YYYY-MM-DD.md` に自動生成し（`crawl.yml` の report ジョブ、`crawler/cmd/report`）、週次でオーナーが目を通す。ファイル先頭の「判定」に要確認の項目が並ぶ。Routine はまずそこを読む
- レポートの「クロール成功率」は、その日の最後の実行が success か partial ならその サイト×日 を成功と数える。分母はサイトごとに最初の実行日以降の日（稼働前を失敗に数えない）。実行記録が無い日は失敗
