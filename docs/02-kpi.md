# 02 — KPIと計測

夜間の自律改善ループは「何を改善と呼ぶか」がなければ動けない。ここがRoutineの北極星。

## Phase 1〜2（データ収集期、最初の3ヶ月）

| KPI | 目標 | 計測方法 | Routineが取れるアクション |
|---|---|---|---|
| クロール成功率 | 95%以上（サイト×日） | `crawl_logs` | 失敗原因の分類、リトライ戦略調整、セレクタ修復PR |
| 抽出精度 | 99%以上（数値が取れた件数/取得件数） | `crawl_logs` ＋ サンプル検証 | セレクタ修復、正規化ルール追加 |
| 対象案件数 | 単調増加 | `offers` の日次件数 | 収集範囲（カテゴリページ等）の拡張PR |
| 索引ページ数 | 単調増加 | Search Console（連携後） | sitemap・内部リンク・構造化データ改善 |
| コスト | 0円 | 各サービスのダッシュボード | 無料枠の残量を監視し、超えそうなら警告 |

### 抽出精度の読み方

`crawl_logs.parsed_count / offer_count` は「還元額を数値化できた割合」で、分母には **還元がポイントではない案件**が含まれる
（保険の一括見積・資料請求の物品プレゼント等。`reward_raw` に文言が入り、`reward_points` と `reward_percent` は null）。
これは修復対象ではなく、数値化率の実質的な上限を下げる要因。2026-09 時点でモッピーは 6 / 1,791 件（0.3%）。

- 真の抽出失敗は `offer_snapshots.reward_raw` が **空**の行。修復（セレクタ・数値化ルール）はこれだけを対象にする
- `reward_raw` に文言があって数値が null の行は、文言を見て「ポイントでない還元」なら放置、「新しいポイント表記」なら数値化ルールを足す
- 目標 99% は数値化率のまま据え置く。ポイントでない案件が増えて届かなくなったら、目標ではなく分母の定義を見直す

## 計測の原則

- 計測できないものは改善対象にしない
- KPIは `docs/02-kpi.md`（このファイル）を単一の真実とし、Routineのプロンプトはここを参照する
- 日次のKPIスナップショットは `reports/YYYY-MM-DD.md` に自動生成し（`crawl.yml` の report ジョブ、`crawler/cmd/report`）、週次でオーナーが目を通す。ファイル先頭の「判定」に要確認の項目が並ぶ。Routine はまずそこを読む
- レポートの「クロール成功率」は、その日の最後の実行が success か partial ならその サイト×日 を成功と数える。分母はサイトごとに最初の実行日以降の日（稼働前を失敗に数えない）。実行記録が無い日は失敗
