# ADR-0006 PR の人間レビューを CI とパスの許可リストで置き換える（自動マージ）

日付：2026-09-25　ステータス：採択（ADR-0004「自律の段階的拡大」の段階 1〜2 を置き換える）

## 背景

ADR-0004 は「初期はセレクタ YAML と docs だけ自動マージ、1 ヶ月事故がなければクローラー変更に広げる」とした。
Phase 1 の 2 日間（2026-09-22〜23）に出た 11 PR（#1〜#11）は、すべてオーナーがレビューしてマージした。

- 人間のレビューが見つけた問題：**0 件**
- 実際に起きた問題：2 件。どちらも CI かデプロイ後の本番実行が見つけた
  - IPv6：ランナーが IPv6 を持たず DB に直結できない。`deploy.yml` の失敗で発覚（#3 → #5）
  - GRANT：初回スキーマに service_role の権限が無く書き込めない。初回クロールの permission denied で発覚（#6）

レビューは待ち時間（オーナーの手が空くまで PR が止まる）だけを生み、検出力は CI と本番実行に劣った。
ADR-0004 の目的「AI 主導開発手法の実践」から見ると、承認待ちは自律ループを止める一番大きな要因になっている。

## 決定

PR のマージ判定を CI に任せる。次をすべて満たす PR は、CI が GitHub の auto-merge を有効化する。

1. CI（`ci.yml` の全ジョブ：go / web / supabase dry-run）が通っている
2. `destructive-migration` ラベルも `needs-owner-review` ラベルも付いていない
3. 変更ファイルが「オーナー承認が必要なパス」に触れていない
4. 同じリポジトリのブランチからの PR で、draft でない

オーナー承認が必要なパス：

| パス | 理由 |
|---|---|
| `.github/**` | ワークフローと CI のスクリプト。自動マージの判定・破壊的 SQL の検出そのものを含む |
| `crawler/internal/policy/**` | クロールの間隔・停止条件・User-Agent（対象サイトへの加害防止） |
| `docs/03-guardrails.md` | ガードレールの定義 |
| `crawler/sites/*.yaml` の新規追加 | 対象サイトを増やす判断。既存ファイルの変更（セレクタの修復）は自動マージ可 |

条件を満たさない PR には CI が `needs-owner-review` ラベルを付け、理由をコメントする（CI 未通過と draft は除く。PR 側で直すもの）。
ラベルは付けるだけで外さない。外すのはオーナー。

### 実装

- `.github/workflows/automerge.yml`：`ci.yml` の完了（`workflow_run`）で起動し、`.github/scripts/automerge-gate.js` で判定する
- 判定を終えた head コミットに commit status `auto-merge-gate` を付け、Branch protection の必須チェックにする
- auto-merge は専用の GitHub App（`AUTOMERGE_APP_CLIENT_ID` / `AUTOMERGE_APP_PRIVATE_KEY`）のトークンで有効化する。マージ方式は merge commit（1 コミット＝1 論理変更の履歴を残す）
- AI（対話セッション・Routine）は自分で `gh pr merge` しない

### 設計上の判断

- **`workflow_run` で起動する**：`pull_request` で起動すると PR 側のワークフローが動くため、`.github/**` を書き換えた PR が自分の判定を書き換えられる。`workflow_run` は常に main の版が動く。判定は API で変更ファイル名とラベルを見るだけで、PR のコードはチェックアウトも実行もしない
- **CI の後に判定する**：破壊的 SQL のラベルは CI の dry-run ジョブが付ける。CI と並行して判定すると、ラベルが付く前にマージされうる
- **commit status を必須チェックにする**：auto-merge は一度有効にすると、新しい push の後も必須チェック（go / web は 20 秒程度で通る）が揃った時点で発火する。新しいコミットに判定の status が無い間はマージされないようにする
- **GitHub App のトークンを使う**：`GITHUB_TOKEN` による操作は後続のワークフローを起動しない。`GITHUB_TOKEN` で auto-merge を有効化すると、マージの push で `deploy.yml` が動かず、マイグレーションもフロントも本番に出ない（日次レポート PR #12 / #14 のマージで CI の push 実行が無いことを確認した）。App は無料で、秘密鍵に期限が無い。PAT は期限があり、オーナー個人の権限に紐づくので採らなかった
- **`.github/**` 全体をオーナー承認にする**：`.github/workflows/**` だけだと、CI が実行するスクリプト（`detect-destructive-sql.sh`、この判定）を書き換えた PR が自動マージされうる

## 却下した案

- レビューを続ける：上記のとおり検出 0 件で、待ち時間だけが残る
- ADR-0004 どおり 1 ヶ月待ってから広げる：待つ間に得られる情報（事故が起きないこと）は、CI と本番実行で既に見えている種類のもの
- パスの禁止リストではなく許可リスト（自動マージしてよいパスを列挙）：コード変更の大半が対象外になり、レビュー待ちが残る。取り返しのつかない変更（ワークフロー・加害防止・ガードレール・対象サイトの追加）だけを止める方が、ADR-0004「ノーガードで運転し、事故が起きたら足す」に合う

## 結果

- オーナーの仕事は `needs-owner-review` の PR と事故対応に絞られる。レビューしない変更が本番に出る
- 事故の検出は CI・デプロイの失敗・日次レポートに頼る。事故が起きたら `logs/incidents/` に記録し、オーナー承認のパスか CI の検査を足す（ADR-0004 の段階 3 は変わらない）
- Branch protection は `strict: false`（最新の main に追随しなくてもマージ可）のまま。自動マージの PR 同士が意味的に衝突しうるが、main の CI とデプロイで検出する。問題になったら `strict` にする
- 判定が失敗した時（App の鍵が無効など）は status が付かず、その PR は止まる。安全側に倒しており、オーナーは管理者権限でマージできる
