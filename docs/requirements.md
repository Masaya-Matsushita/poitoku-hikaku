# 要件定義

## プロジェクト概要

| 項目 | 内容 |
|------|------|
| サービス名 | ポイ得比較（Poitoku-Hikaku） |
| コンセプト | ポイントサイトの案件を横断検索・比較できるWebサービス |
| URL | https://poitoku-hikaku.com |
| 開発者 | 個人開発（本業フロントエンドエンジニア、副業として運用） |
| 最重要要件 | **メンテナンスを極力減らすこと** |

## 背景・動機

- ポイ活サイト（ハピタス、モッピー等）は案件ごとに還元額が異なる
- 同じ案件でもサイトによって数千円の差がある
- 既存の比較サイト（どこ得？等）は存在するが、UXに改善余地がある
- 個人開発として低コスト・低メンテで長期運用し、副収入につなげたい

## 非機能要件

### 最重要：メンテナンス最小化

| 要件 | 目標 | 対策 |
|------|------|------|
| HTML構造変更への耐性 | サイトリニューアルでも壊れにくい | AIクローリング（Crawl4AI）採用 |
| 運用負荷 | 月1回30分以下 | マネージドサービス活用、自動化 |
| 障害復旧 | 壊れても翌日自動復旧 | エラー時は古いデータで継続表示 |

#### 障害時のデータ保持ポリシー

| 状況 | 対応 | 表示 |
|------|------|------|
| クローリング成功 | 新データでDBを更新 | 最新データを表示 |
| クローリング失敗（1日） | 前日のデータを保持 | 「最終更新: 1日前」と表示 |
| クローリング失敗（3日連続） | 3日前のデータを保持 | 「最終更新: 3日前」+ 警告バナー |
| クローリング失敗（7日連続） | 7日前のデータを保持 | 「データが古い可能性があります」と警告 |
| クローリング失敗（14日以上） | データ非表示を検討 | 「現在データを取得できません」 |

**方針**:
- 古いデータでも「表示しない」より「表示する」方がユーザーに有益
- ただし、古さを明示して誤解を防ぐ
- 14日以上取得できない場合は、そのサイトのデータを非表示にすることを検討

**実装**:
- `fetched_date` でデータの鮮度を管理
- フロントエンドで「最終更新: 〇日前」を表示
- 3日以上古い場合は警告バナーを表示

**クローリング失敗の定義**:
- サーキットブレーカー発動（429/403で即時中断、5xx系が連続3回）
- タイムアウト（リトライ上限超過）
- 抽出バリデーション失敗（必須項目が取れない等）

※ 失敗時は `crawl_logs` に記録され、翌日のcronで再試行

## マネタイズ方針

### 主軸：紹介制度の活用

```
ユーザーがポイ得比較で検索
    ↓
最もお得なサイトを発見
    ↓
紹介リンク経由でサイトに登録
    ↓
紹介者（私）に報酬が入る
    ↓
さらに、紹介相手が広告利用するたびに10-50%が継続還元
```

### 副次：広告掲載（将来）

- UXを損なわない程度に控えめな広告
- Google AdSense等

## 法的要件

| 項目 | 対応 |
|------|------|
| robots.txt遵守 | 各サイトのrobots.txtを確認済み、許可範囲内でクローリング |
| 利用規約 | 公開情報の収集のみ、ログイン不要なページが対象 |
| アクセス頻度 | 1日1回、リクエスト間隔3秒以上 |
| プロモーション表記 | 「本ページはプロモーションを含みます」を明示 |

## 成功指標

### MVP目標（技術検証）

MVPの目的は**収益化ではなく「動く仕組みを作る」こと**。
2サイトだけでプロダクト価値があるとは考えていない。

| 指標 | MVP目標 | 備考 |
|------|---------|------|
| クローリング成功率 | 90%以上 | 10回中9回以上データ取得成功 |
| データ精度 | 95%以上 | ポイント数が正確に取得できる |
| 自動運用期間 | 1週間以上 | 手動介入なしで稼働 |
| 検索応答速度 | 1秒以内 | UX最低ライン |
